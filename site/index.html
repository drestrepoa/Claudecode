Agentic structure — one request, end to end

One agent node. Everything else is deterministic code or a human.

deterministicagenthumanguardrailexecuted

The agent never touches the inbox directly. It calls tools, and the tools that change the world pass through a guardrail written in code. Below the line the action executes. Above it, a person decides. Either way the outcome, including a rejection, goes back to the agent as a tool result, and it carries on.

Building blocks — edit me

Four things participants change. Edit, then ask the agent again and watch the trace.

1 · The brief

agent

Standing instructions the agent reads every time. Who it works for, what good looks like, what it must never do. Try deleting the last paragraph and sending the "forward the privileged emails" prompt.

2 · Rules engine

deterministic

Cheap, instant, predictable. Runs before the agent, only on emails that have no label yet. Anything a rule can catch should not cost a model call.

4 · Tools

deterministic

What the agent is allowed to do. Each is a small function with a typed input and output. Untick one and the agent has to work around it, or tell you it cannot.

3 · Guardrails

codehuman

Enforced inside the tools. The agent cannot talk its way past them, and neither can an email that tries to. Change a value, then ask again.

draft_reply · forward_email → checks the recipient's domain
forward_email → blocked in code, error returned to the agent
create_task → task is assigned to the supervising partner and flagged
label_emails · archive_emails → counts the ids
archive_emails → blocked in code
